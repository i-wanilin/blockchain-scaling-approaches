  The MEASUREMENTS in this file are valid. The INTERPRETATION is not.

  This run claimed 4 tx/s is a "per-account limit". It is not. A later run with
  the concurrency defect fixed got 113.80 tx/s FROM A SINGLE ACCOUNT
  (arbitrum-single-account-2026-09-08.txt).

  The real relationship is:  throughput = concurrency / submission latency.
  4 tx/s is simply ONE in-flight request divided by ONE 250 ms block interval.

  Why this run got it wrong: the probe used one thread per ACCOUNT, and since
  eth_sendRawTransaction blocks, that thread serialised its own sends. The
  `depth` column therefore never varied real concurrency - a defect this file
  already documents below, but whose implication was missed.

--------------------------------------------------------------------------------
WHAT EACH NUMBER MEANS
--------------------------------------------------------------------------------

The life of one transaction in this probe:

  step 0  sign it                      <- done BEFORE timing starts (pre-signed,
                                          so ECDSA cost cannot inflate results)
  step 1  call eth_sendRawTransaction  <- TIMER STARTS
  step 2  sequencer receives + queues it
  step 3  sequencer seals a block      <- ~every 250 ms, but ONLY if something
                                          is queued (this chain has no clock;
                                          idle = zero blocks, verified)
  step 4  the send call returns        <- it BLOCKS until step 3. This is the
                                          key property of this node.
  step 5  poll eth_getTransactionReceipt until it appears
  step 6  receipt in hand              <- TIMER STOPS

  sub_ms    steps 1->4.  How long eth_sendRawTransaction blocks for.
            Measured ~244 ms in EVERY cell. Because the call is synchronous,
            this is really "how long until my transaction was sealed".

  e2e_mean  steps 1->6.  Submission plus fetching the receipt.
  e2e_med   same, median.
  e2e_p90   same, 90th percentile.

  span_s    wall time, first send starting to last receipt arriving.
  sub_tps   transactions ACCEPTED per second (steps 1->4 completing).
  inc_tps   transactions CONFIRMED IN A BLOCK per second (steps 1->6).
            This is the throughput figure that matters.
  ok/sent   receipts obtained / submissions accepted. err = failures.

WHY sub_ms AND e2e_mean ARE NEARLY EQUAL AT depth=1
  244.6 vs 246.5 ms. Because the send call already waited for sealing, the
  receipt is available almost immediately afterwards. Nearly all the latency
  is in step 3 - waiting for the sequencer to seal - not in step 5.

WHY inc_tps == 1 / sub_ms PER ACCOUNT
  1 / 0.244 s = 4.10 /s, and every single-account cell measured 3.98-4.06 /s.
  A synchronous, nonce-ordered submit means an account can have only ONE
  transaction in flight at the sequencer. Its rate is therefore pinned at
  1/(submission latency). Adding accounts adds parallel submitters, so the
  aggregate scales linearly. Confirmed by block contents: blocks during the
  8-account phase held 9 transactions each, so the sequencer does batch.

--------------------------------------------------------------------------------
KNOWN DEFECT IN THIS RUN - the depth column measures nothing
--------------------------------------------------------------------------------

  The `depth` axis was meant to test whether one account can pipeline several
  transactions. IT DID NOT TEST THAT.

  The probe runs one thread per ACCOUNT. Since eth_sendRawTransaction blocks
  for ~244 ms, that single thread serialises its own sends: 16 sends take
  16 x 244 ms = 3.9 s. That is exactly the e2e_mean of 3755 ms at depth=16.

  So the rising e2e latencies down each depth column are THE PROBE'S OWN QUEUE,
  not the node's behaviour. The tell is that inc_tps stayed flat (4.06, 4.06,
  4.05) across all three depths - the node never noticed.

  To test pipelining properly: one thread per IN-FLIGHT SLOT, not per account.

  Consequence: it is NOT yet proven that a single account cannot exceed ~4 tx/s.
  Strongly suggested, not established.

  RESOLVED 2026-09-08: it was disproved. With one thread per IN-FLIGHT SLOT
  instead of per account, a single account scales linearly with concurrency all
  the way to 113.80 tx/s at 32 in flight, zero errors. The "strong suggestion"
  above was an artifact of the defect described in this very section.

--------------------------------------------------------------------------------
SCOPE - what these numbers are not
--------------------------------------------------------------------------------

  This is a local development testnode, not Arbitrum One. Production Arbitrum
  operates orders of magnitude above these figures and its sequencer does not
  block for 244 ms on submission. These numbers characterise THIS DEPLOYMENT.
  What transfers is the mechanism and the cost structure, never the rate.

  Also: 120 tx per cell is a probe, not an n=3 measurement run. Generator and
  node share one host, so a plateau must always be checked against CPU load
  (it was 0.25-0.94 throughout here, so the linear scaling is genuine).
